# 11 静的UI契約・インタラクション・演出レイヤー

## 一言でいうと

**静止画で決められるものは先に契約し、振る舞いが必要になったところだけ状態設計へ切り替える。**

AIや別の実装者へUIを渡すとき、すべてを「いい感じに実装してください」とすると、実装段階でデザイン判断が再発生します。

そこでDesign FEでは、UIを次の3層に分けて考えます。

1. **静的UI契約**
2. **インタラクション仕様**
3. **演出レイヤー**

この3つを混ぜないことが、再現性と保守性を上げる基本方針です。

---

# 1. 静的UIは紙から契約できる

## 紙プロトタイプの役割

紙は「雑なラフ」に限りません。

位置・比率・余白・優先順位まで詰めれば、実装者へ渡す**視覚仕様書**として使えます。

紙の段階で最低限決めるもの：

- 画面内の主要要素
- 各要素の相対位置
- サイズ比率
- 主役と補助要素の関係
- ネガティブスペース
- 視線の流れ
- 要素同士の距離
- 表示領域
- タップ領域
- 侵入してはいけない空間

重要なのは、**見えている領域と操作できる領域を分けて設計できること**です。

例えば雲型の選択肢なら、

- 見た目は不均一な雲
- タップ領域は十分な矩形
- 隣接選択肢との境界は明確
- 案内役のネガティブスペースには侵入しない

という設計が可能です。

## visual bounds と hit bounds

見た目の領域と操作領域は一致する必要がありません。

- **visual bounds**: 利用者に見えている形
- **hit bounds**: タップ・クリックを受け付ける領域

「タップ領域を広げるために見た目まで広げる」は、必ずしも正しい修正ではありません。

操作性は hit bounds で改善し、世界観は visual bounds で守る、という分離ができます。

---

# 2. 契約実装

静的UIを十分に詰めた後は、実装を「新しいデザインを考える工程」ではなく、**契約を再現する工程**として扱えます。

## 契約に含めるもの

- 位置
- 大きさ
- 比率
- 余白
- タイポグラフィ
- 色
- visual bounds
- hit bounds
- 不変条件
- レスポンシブ時に守る優先順位
- 完成見本

## 実装者へ残さない判断

次のような判断を実装段階へ残さないことが理想です。

> ここ、空いているから詰めた方がよいか？

> 3つのカードは同じ幅に揃えた方がよいか？

> タップ領域を稼ぐために見た目も広げるか？

これらが設計時に決まっていれば、実装者やAIは「改善」ではなく「再現」に集中できます。

## 検証

契約実装では、完成条件も明確にします。

- 指定画面幅でレンダリングする
- 原案と同一サイズで比較する
- 位置・サイズ・余白の差を見る
- hit bounds を確認する
- 主要端末で操作する
- 「動く」だけでなく「原案との差分が許容範囲か」を確認する

---

# 3. 静止画だけでは足りなくなる境界

静止画契約は強力ですが、UIの状態変化がレイアウトへ影響し始めると、それだけでは足りません。

例えば、

> カードを押す  
> → カードが展開する  
> → 背景が暗くなる  
> → キャラクターが後退する  
> → 他の選択肢が操作不能になる

この場合、開始画面と終了画面だけ決めても、途中の振る舞いが未定義です。

ここからは**インタラクション仕様**が必要になります。

---

# 4. 「画面」ではなく「状態」を設計する

静的UIは、ある瞬間の完成状態です。

動的UIでは、

```text
State A
  ↓
Transition
  ↓
State B
```

として設計します。

## 状態と進捗を分ける

意味上の状態と、アニメーション途中の進捗は分けます。

```text
state = Opening
progress = 0.42
```

- **state**: いま何をしているか
- **progress**: どこまで進んだか

この分離により、設計側は「Opening中に何が起こるか」を記述しやすくなります。

---

# 5. どこまでを一つの状態として管理するか

コンポーネントごとに状態を持てばよいとは限りません。

判断基準は、

> **一緒に変わらないと見た目・意味・操作が壊れるものは、同じ状態から派生させる。**

です。

## 2〜3要素の連動

例えば、

- カードが開く
- 背景が暗くなる
- キャラクターが少し後退する

程度なら、1つの画面状態から派生させれば比較的管理しやすいです。

## 5〜6要素以上が連動する場合

要素が増え、

- Aが動く
- Aに押されてBが移動する
- Bの移動でCの余白が変わる
- Cの変化でDのタップ領域が変わる
- 途中でEが操作される

のように因果が連鎖すると、コンポーネント単位の管理は急激に難しくなります。

この場合は、

```text
SceneState
- Idle
- Selecting
- Confirming
- Transitioning
```

のように**シーン全体の状態**を唯一の真実にし、

```text
Character  ← SceneState
Cloud      ← SceneState
Background ← SceneState
Buttons    ← SceneState
Text       ← SceneState
```

と各要素を派生させる方が安全です。

個別の boolean が増えると、

```text
characterMoved = true
cloudExpanded = false
backgroundDimmed = true
```

のような「存在してほしくない組み合わせ」が増えていきます。

---

# 6. インタラクションの難易度は連続性で跳ねる

「インタラクティブ」と一括りにせず、難易度を分けて考えます。

## Level 1: 離散的な入力

- ボタン
- タブ
- チェック
- 単純な画面遷移

比較的仕様化しやすい。

## Level 2: 状態で見た目が変わる

- 選択状態
- モーダル
- アコーディオン
- 展開 / 折りたたみ

開始状態と終了状態、遷移条件を定義すれば管理しやすい。

## Level 3: 複数要素が連動する

2〜3要素なら比較的扱いやすい。

5〜6要素以上が同時に意味を変えるなら、SceneStateを検討します。

## Level 4: 遷移途中へ利用者が介入できる

- ドラッグ
- スワイプ
- 途中キャンセル
- 連続操作
- 方向転換

ここから難易度が大きく上がります。

```text
progress = 0.0 ... 1.0
velocity
direction
pointer state
cancel
snap destination
```

のように、状態が離散値だけでは表現できなくなります。

## Level 5: 物理的・自由な操作

- 慣性
- 自由配置
- 多点ジェスチャ
- 物理シミュレーション

ゲームUIに近い設計領域です。

---

# 7. 全フレームを作る必要はない

動的UIを究極まで作り込むと、映画制作の絵コンテに近づきます。

しかしUIは映画と違い、利用者が途中で介入します。

そのため、全フレームを固定するより、

- 開始キーフレーム
- 重要な中間キーフレーム
- 終了キーフレーム
- 不変条件
- 禁止領域
- 変化の順序
- 所要時間
- 中断時の挙動

を定義する方が実用的です。

## 例

```text
開始: Closed
終了: Open

不変条件:
- タイトル位置は固定
- キャラクター領域へ侵入しない
- 他の選択肢は遷移中操作不可

変化:
- card height: 120 → 240
- detail opacity: 0 → 1
- icon rotation: 0° → 180°

順序:
1. カード展開開始
2. 60%地点から詳細文を表示
3. 展開完了後に追加操作を許可

duration: 250ms
```

# 8. 演出レイヤー

すべての「動き」がインタラクションではありません。

背景動画、走る小さなキャラクター、鳥、光、パーティクルなど、なくても機能が成立するものは**演出レイヤー**として分離できます。

## 演出レイヤーの原則

- UIレイアウト計算へ参加しない
- 重要情報を持たせない
- 主要操作の hit bounds を変えない
- 状態機械の必須条件にしない
- 再生失敗しても操作できる
- reduced motion でも成立する
- 主役を邪魔しない

## 良い分離

```text
背景
↓
装飾アニメーション
↓
本体UI
↓
必要なら前景エフェクト
```

例えば画面下を小さなキャラクターが走る演出は、本体UIとは独立してよい場合があります。

```text
RunnerState
- Hidden
- Running
```

本体のSceneStateとは無関係に動けるなら、分離した方が安全です。

---

# 9. リッチさと複雑さを混同しない

重要な設計判断です。

**リッチなUIにするために、複雑なインタラクションを増やす必要はありません。**

例えば、

- 利用者の操作は単純なタップ
- UI状態は離散的
- 背景だけゆっくり動く
- タップ時に雲が少し反応する
- ときどき小さなキャラクターが走る

なら、見た目は豊かでも状態空間は比較的小さく保てます。

Design FEでは、

> **インタラクションは必要以上に複雑化しない。リッチさは独立した演出で稼ぐ。**

を、個人開発やAI実装で有効な基本戦略として扱います。

---

# 10. 3層モデル

最終的には次のように整理します。

## ① 静的UI契約

責任を持つもの：

- 位置
- サイズ
- 余白
- 視覚的階層
- visual bounds
- hit bounds
- タイポグラフィ
- 色
- 完成状態

**紙 → 必要ならFigma等で寸法化 → 契約実装**

が使いやすい領域です。

## ② インタラクション仕様

責任を持つもの：

- 状態
- 状態遷移
- 中間状態
- 複数要素の連動
- 割り込み
- キーフレーム
- 不変条件

**状態機械＋制約**として設計します。

## ③ 演出レイヤー

責任を持つもの：

- 雰囲気
- 世界観
- 楽しさ
- 一時的な視覚効果

本体UIからできるだけ独立させます。

# 判断フロー

```text
その要素は静止画で決められる？
  ├─ Yes → 静的UI契約
  └─ No
      ↓
その動きが機能・意味・操作に必要？
  ├─ Yes → インタラクション仕様
  └─ No  → 演出レイヤー
```

さらに、インタラクション仕様で複数要素が連動する場合：

```text
独立して変化しても壊れない？
  ├─ Yes → コンポーネント状態
  └─ No  → 共通のSceneStateを検討
```

# AIへの指示例

```text
この画面は次の3層を分離して実装してください。

1. 静的UI契約
- 添付原案の位置・比率・余白を変更しない
- visual bounds と hit bounds を分離する
- タップ領域確保を理由に見た目を拡大しない

2. インタラクション
- 選択時の状態は ScreenState から派生させる
- 個別 boolean を増やして状態を組み合わせない
- 遷移中も指定した不変条件を守る

3. 演出
- 背景動画・装飾キャラクターはレイアウト計算へ参加させない
- 演出が停止しても全操作を可能にする
- 重要情報を演出に依存させない

完成後は静的状態のスクリーンショット比較と、全状態遷移の実機確認を行ってください。
```
